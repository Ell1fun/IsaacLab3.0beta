重构后的主线

当前代码从“一个大 orchestrator 文件”拆成多个模块。主流程仍然是：用户输入 → route → spec builder → preset enrichment → placement → schema gate → template generator → writer。 变化在于：每一步的实现被放到了独立模块，方便后续扩展和排错。

模块职责

文件职责什么时候看它
orchestrator.pyCLI 入口、argparse、chat loop、命令分发。命令行参数、交互式输入、输出格式有问题时。
pipeline.py把 Stage A、schema gate、Stage B、writer 串成完整流水线。想理解一次 generate/chat 的整体顺序时。
spec_builder.py本地关键词 parser；必要时调用 LLM 补齐 spec。自然语言没识别出机器人/物体，或 API fallback 行为有问题时。
presets.py加载 presets、解析继承、补齐仓库事实、计算 placement。EEF/link/joint/USD/object pose/target pose 不对时。
schema_validation.pyschema gate 和 jsonschema 缺失时的兜底校验。spec 明明生成了但不能进入 generator 时。
generator_workflow.pytemplate generator、env_cfg 薄封装、注册内容、启动命令、写文件。生成文件内容、注册 task、命令或 dry-run/write 行为有问题时。
llm_client.py统一封装模型 API 调用、timeout、retry、Ark responses 支持。API 慢、超时、返回格式异常时。
registry.pyskill registry 和 route_skill。用户 prompt 没有路由到 pick_place_vr 时。
config_loader.py读取 local config、环境变量、CLI override、dry-run/write gate。API key、model、timeout、--write 行为不符合预期时。
env_utils.py路径、YAML/JSON、deep_fill、缺失值判断等通用工具。多个模块共用的底层工具行为需要改时。
starter_specs.pystarter spec 示例。使用 template --skill pick_place_vr 时。

orchestrator.py 现在做什么

重构后，orchestrator.py 只保留 CLI 相关逻辑。它不再直接知道如何算 placement、不直接渲染 env_cfg、不直接发 HTTP 请求。 

main(argv):
  1. build_parser() 创建 route/template/validate/generate/chat 子命令
  2. skills_registry() 构建本地 skill registry
  3. 根据 args.cmd 分支：
     - route: route_skill
     - template: starter_specs.template_pick_place_vr_spec
     - validate: schema_validation.validate_spec
     - generate: pipeline.run_generate_pipeline
     - chat: run_chat_loop + pipeline.run_generate_pipeline

为什么这样拆

旧问题拆分后的变化
所有函数都在一个文件里，继续加逻辑会越来越难读。按职责分模块，每个文件只处理一个方向。
LLM 调用、template generator、writer 混在一起，边界不清。LLM 只在 llm_client.py 和 spec builder fallback 里出现。
placement 规则和 object preset 补齐混杂在大文件中。统一放在 presets.py，因为它属于仓库事实和工作空间规则。
生成失败时，不容易判断是路由、schema、preset、API 还是 generator 的问题。可以按模块定位错误。
