2026-07-08：工程化评审

今天对 my_docs/env_cfg_skills 做了一次工程化评审。结论是： 当前流程已经不是简单 prompt demo，而是具备 schema + presets + prompts + workflow + gate + dry-run 的本地 skill 雏形；但距离长期可维护、可落地的生产级 skill 还需要补齐配置一致性、路径契约、示例同步和运行级验证。

发现的 5 个问题

编号问题为什么重要状态
1 robot_presets.yml 中的 output_dir / registration_module 没被 generator 消费。 preset 看起来配置了输出位置，但生成器仍写死 pick_place 目录，扩展时容易误判配置已经生效。 已修复
2 object_presets.yml 中的 pose / default_target_pose 语义不闭合。 维护者可能以为 object preset pose 会影响生成结果，但当前默认位置主要由 robot placement 计算。 待处理
3 examples/ 与当前 presets/ 存在事实漂移。 示例里的 joint/link 命名如果过期，会误导模型、测试和后续维护者。 待处理
4 post_generation_tests.py 主要是静态检查，不能证明 env_cfg 可 import 或可创建环境。 AST 通过不代表 IsaacLab 运行通过；还需要 import/registry/env smoke test。 待处理
5 schema enum 和 presets key 如果都手写维护，会形成两套事实源。 新增机器人/物体时应该只改 presets；schema 的允许值应由 presets 派生。 已修复

本次优先修复

问题 5：schema enum 由 presets 派生

在 schema_validation.py 中新增运行时 schema resolver。 每次校验 pick_place_vr spec 前，先复制一份 schema，并把 preset enum 注入为当前 presets keys：

  • robot.preset.enum 来自 presets/robot_presets.yml resolved keys。
  • object.preset.enum 来自 presets/object_presets.yml keys。
  • 磁盘上的 schema 只保留结构约束，enum: [] 是运行时占位，不再手写具体 preset 列表。
  • 以后新增或重命名 preset key，只需要改 presets；schema gate 会自动使用新的允许值。
  • 即使本地环境没有 jsonschema，fallback validator 也会检查 preset key 是否存在于 presets 文件。

问题 1：generator 消费 preset 输出路径

在 generator_workflow.py 中新增 output_paths_for_spec()。 template generator 和 adaptation generator 都改为从目标 robot preset 读取：

  • output_dir：决定 auto env_cfg 文件写到哪个目录。
  • registration_module：决定 task 注册内容 patch 到哪个 __init__.py。
  • 如果 preset 没配置，则 fallback 到当前 pick_place 默认路径。

后续顺序

  1. 继续处理问题 3：让 examples 与 presets 同步，避免示例事实漂移。
  2. 处理问题 2：明确 object preset pose 的语义，删除无效字段或真正消费它们。
  3. 处理问题 4：把 post-generation gate 从静态检查升级到 import/registry smoke test。
  4. 再补 skill manifest 或更标准的注册入口，让当前本地 skill 更接近平台级 skill。

2026-07-08：examples 对齐 presets

将 examples/g1_pick_place_hand_tracking 与 examples/r11_pick_place_hand_tracking 改成当前 presets enrichment 后的 spec 快照。 这样 examples 不再携带旧 hand joint、TODO object USD 或旧命名规则。

  • examples/ 当前不会被 orchestrator、pipeline、spec builder 或 generator 在运行时读取。
  • 用户调用 skill 时，examples/ 不会影响路由、schema gate、preset enrichment 或 env_cfg 生成。
  • 当前 workflow 也不会自动增删改 examples/ 文件；只有人工维护或未来显式测试脚本才会使用它们。
  • 如果未来把 examples 接入回归测试，应只读这些文件，并用它们验证输出摘要，不应在普通生成流程中修改它们。

2026-07-08：阶段 A/B 多物体摆放

在当前单主 pick_place skill 上增加“附加场景物体 + 语义摆放”的最小安全能力。 本轮不修改 success、termination、reward 或 observation；主 object 仍然是唯一参与 pick-place 判定的物体。

  • 新增 presets/placement_presets.yml，维护 near_left_hand、near_right_hand、table_center、table_back、table_front 等语义摆放点。
  • 扩展 schema：主 object 支持 placement.semantic，新增可选 scene_objects[]。
  • 扩展 presets.py：从 placement preset 计算主物体和附加物体的 pose，并继续从 object preset 补 USD/scale/single_rigid_body。
  • 扩展 generator_workflow.py：把 scene_objects 渲染成额外 RigidObjectCfg，不替换 self.scene.object。
  • 扩展 schema_validation.py 和 post_generation_tests.py：检查 scene object preset/name/semantic，并确认生成内容包含对应物体。
  • 扩展 pick_place_vr_spec_builder.md 和本地 parser：用户说“方向盘放右手附近，桌上摆水瓶”时，主方向盘使用 near_right_hand，水瓶进入 scene_objects。
明确边界：如果用户说“水管和方向盘都要抓取”，当前阶段不能自动生成多主物体成功条件；应追问主操作物体，或后续进入阶段 C 设计多主任务。

2026-07-08：Object Intent Clarification Gate

增加 spec 生成前的物体意图澄清 gate，避免模型在主物体不清晰或物体不在 presets 中时擅自生成 env_cfg。

  • 给 object_presets.yml 增加 aliases、description、status、blocked_reason。
  • 新增 object_intent.py，从用户 prompt 中识别已知物体、未知物体、主操作物体候选和 blocked preset。
  • 在 spec_builder.py 的 Stage A 最前面调用 object intent gate；如果需要澄清，直接返回 questions，不进入 enrichment、schema 或 generator。
  • 未知物体会推荐当前 ready 的 object presets，并询问用户是改用已有物体、提供 USD 新增 preset，还是本次不添加。
  • 多个可能主操作物体会追问用户选择唯一主 object，其余物体只能作为 scene_objects。

2026-07-08：多轮 Clarification Resolver

将上一版“直接扫描完整历史文本”的 object intent gate 改成“多轮 draft intent + resolver + safety gate”。 这样用户回答“不要水管了”时，会从当前 intent 中删除水管，而不是因为历史 prompt 里仍包含“水管”而反复阻断。

  • 新增 clarification_resolver.py，负责构造和更新 draft_intent。
  • orchestrator.py 的 chat loop 现在保存上一轮 draft_intent，每轮只把用户最新回答传给 pipeline。
  • pipeline.py 和 spec_builder.py 透传并输出更新后的 draft_intent。
  • resolver 负责理解删除/保留/主物体选择等多轮意图；deterministic safety gate 继续检查未知物体、blocked preset 和多主物体歧义。
  • 验证场景：第一轮“水瓶主物体 + 方向盘附加 + 排气管 + 水管”会阻断；第二轮“不要水管”后只剩排气管阻断；第三轮“排气管也不要”后生成水瓶主物体和方向盘附加物体。

  • spec_builder.py 在开启 API 时优先调用 LLM resolver；模型失败时回退规则 resolver。

2026-07-08：Post Validation 增强（桌面摆放 + 可达性）

在 generator 写文件前增加两步轻量验证，避免“看起来生成成功，但一启动就明显不可用”的场景摆放问题。 这两步都不需要拉起仿真环境；它们只依赖最终冻结的 spec（桌子 pose、各物体 pose、placement 语义等）。

  • 桌面范围检查：验证主物体与附加物体的 pose.pos 是否落在桌面 XY 合理范围内。
  • 最小间距检查：对所有生成的物体做成对距离检查，避免多个物体生成在几乎同一位置。
  • 可达性启发式检查：当 robot preset 提供 idle_wrist_pose 时，根据 near_left_hand/near_right_hand 语义选择对应手腕参考点，检查物体与手腕的距离不超过阈值。
  • 严格 IK 检查：当 robot preset 提供 urdf_path、controlled_joint_names、eef_link_names 且启用 reachability.strict_ik.enabled 时，使用 Pinocchio 做不启动仿真的 position IK 收敛检查。
  • 严格 IK 的 required 默认为 false：缺少 Pinocchio/URDF 时不误杀 demo；如果产品阶段要求强保证，可改成 true，缺依赖或 IK 不收敛都会阻断交付。
  • 若检查失败：post-generation gate 阻断交付，不写文件，优先调整 placement preset / robot preset 或用户语义摆放选择。
