AI Agent 生成 env_cfg：Adaptation 与 Test Gate

说明 exact template、template adaptation、unsupported 三档路由，以及为什么用自动测试 gate 替代人工核查。

核心原则

生产工程里不应该让 AI 随意写最终 env_cfg。当前策略是： 能精确匹配模板就不用 AI；缺模板时 AI 只生成 adaptation_spec； 最终 Python 文件由程序确定性生成，并必须通过自动测试 gate。

三档路由

级别触发条件行为是否写文件
Level 1: Exact Template robot、object、input_source 都能在 presets/template 中精确匹配。 直接走 deterministic template generator，不调用 AI。 通过自动 tests 后，dry-run 输出路径；带 --write 才写文件。
Level 2: Adaptation Candidate robot/object 存在，但当前 robot 没有该 input_source 模板；仓库里存在其他 robot 的同 input_source 参考模板。 输出 adaptation candidate；启用 API 时让 AI 生成 adaptation_spec，再由程序生成 candidate env_cfg。 默认不写。只有 candidate env_cfg 自动 tests 全通过，才允许 dry-run 或 --write。
Level 3: Unsupported robot preset、object preset、参考 input_source 或基础资产缺失。 阻断，进入后续独立 asset onboarding skill。 不写。

G1 + Motion Controller 的当前行为

当 prompt 是“宇树 G1 motion controller 抓水瓶”时，local parser 会得到： robot.preset=unitree_g1_inspire_ftp、 object.preset=bottled_water_c01、 control.teleop.input_source=openxr_controller。

之后 generator 会检查 unitree_g1_inspire_ftp.supported_teleop_templates.openxr_controller。 当前没有这个模板，所以不会误用 G1 handtracking 模板。不开 API 时只输出 adaptation candidate； 开启 --enable_api 时，会让模型输出 adaptation_spec，再由程序确定性生成候选 env_cfg。

代码位置

当前它们还不是两个独立的 skill，而是 pick_place_vr skill 里的两个 workflow 模块。 这样做是为了先把闭环跑通：用户 prompt 进入同一个 orchestrator，由 pipeline 决定走 exact template、AI adaptation，还是 validation gate。

能力当前代码位置职责后续是否可拆成 skill
G1 motion controller adaptation env_cfg_skills/generator_workflow.py run_adaptation_generator_workflow() 在没有 exact template 且 --enable_api 打开时触发； 它读取 prompts/pick_place_vr_template_adaptation.md， 再把 G1 handtracking、G1 controller 参考、R11 tri motion controller 参考抽成结构化片段包，连同 spec 发给模型； 模型只返回 adaptation_spec，Python env_cfg 由 workflow 确定性渲染。 可以，后续可拆成 template_adaptation skill。
自动 validation / test gate env_cfg_skills/post_generation_tests.py run_post_generation_tests() 在写文件前执行； 候选 env_cfg 语法不对、包含 TODO、注册缺 task id、命令不可复制都会被拦截。 可以，后续可拆成 env_cfg_validation skill。
总调度 env_cfg_skills/pipeline.py run_generate_pipeline() 负责把 spec builder、generator/adaptation 和 validation gate 串起来。 不建议拆成 skill，它更像 orchestrator 内部 workflow。

为什么做结构化抽取

最早的 adaptation 做法是把两份 env_cfg 全文发给模型。这样上下文接近两万 tokens，API 容易变慢； 如果简单 truncate，又可能刚好截掉 controller pipeline、retargeter、output reorder 这些关键代码。 所以现在改成 structured snippets：不截断全文，而是用 AST 抽取和迁移相关的 import、class、function、常量片段。

方式问题当前选择
整份 env_cfg 全文tokens 多、请求慢、模型注意力分散。不用作主路径。
固定长度截断可能截掉关键 pipeline，导致模型误判无法迁移。不再默认使用。
结构化片段抽取需要维护抽取规则。当前采用：保留 EnvCfg、teleop、pipeline、controller、source、retargeter、action、hand、trigger 等相关 symbol。
 
generator_workflow.extract_env_cfg_adaptation_context(...)
  - ast.parse(env_cfg_source)
  - 保留 imports
  - 保留相关 class/function/constant
  - 输出 source_path / source_chars / extracted_chars / symbols
  ↓
build_adaptation_messages(...)
  - prompt
  - spec
  - requested_robot_existing_reference_env_cfg_context
  - same_input_source_reference_env_cfg_context

R11 Motion Controller 参考源选择

R11 当前有两份 motion controller 相关参考： pickplace_seres_r11_env_cfg.py 现在只保留 R11 hand tracking 主任务； pickplace_seres_r11_tri_env_cfg.py 里把 controller retargeter、trigger/squeeze、手部 open/closed pose、TensorReorderer 说明得更完整。

因此 workflow 现在统一为： 所有 R11 motion controller 的运行入口和 adaptation 参考材料都使用 pickplace_seres_r11_tri_env_cfg.py。 这样避免同一个输入源在两个文件里维护两套实现。 

robot_presets.yml:
  seres_r11_a2_high_pd:
    supported_teleop_templates:
      openxr_controller:
        module: pickplace_seres_r11_tri_env_cfg
        class: PickPlaceR11TriEnvCfg
        adaptation_reference_env_cfg: pickplace_seres_r11_tri_env_cfg.py
        adaptation_reference_class: PickPlaceR11TriEnvCfg

Prompt 和 Workflow 的边界

adaptation 的模型提示词现在放在 env_cfg_skills/prompts/pick_place_vr_template_adaptation.md。 这属于 skill 的可维护资产；generator_workflow.py 只负责读取 prompt、拼接上下文、调用模型和解析输出。

部分放在哪里负责什么
Prompt prompts/pick_place_vr_template_adaptation.md 告诉模型迁移规则、输出 JSON 格式、禁止 TODO/伪代码、无法安全迁移时输出 blocked_reason。
Workflow generator_workflow.py 判断什么时候需要 adaptation，读取 prompt，抽取参考 env_cfg 片段，注入 spec 和结构化上下文，调用模型。
Validation post_generation_tests.py 程序渲染候选 env_cfg 后，检查语法、TODO、注册、命令，以及 G1 trigger hand joint coverage，决定能不能写文件。

G1 Trigger 合拢策略

对 G1 + motion controller，模型不再直接写 Python。模型只输出 G1MotionControllerAdaptationSpec，其中最关键的是 wrist offset 和 24 个 Inspire hand joints 的 open/closed pose。 workflow 再生成 G1ControllerTriggerGraspRetargeter： 

grasp = max(trigger, squeeze)
joint_value = open_pose[joint] + grasp * (closed_pose[joint] - open_pose[joint])

这样用户按 trigger 或 squeeze 时，机器人手会从 open pose 连续插值到 closed pose。 post_generation_tests.py 会检查 open/closed pose 是否覆盖全部 24 个 G1 Inspire hand joints，防止模型漏关节。

为什么不做人工核查

人工核查容易遗漏 action layout、joint 顺序、retargeter 输入输出、注册路径这类细节。 更适合工程化的方式是把验收规则写成 test gate：只要生成文件，就必须先跑自动检查。

检查类型当前实现后续增强
语法检查ast.parse 检查生成的 Python 内容。进一步执行 py_compile 到临时文件。
占位符检查禁止生成内容包含 TODO。扩展到 link/joint/path 的 known-bad placeholder。
注册检查__init__.py 内容必须包含生成的 gym_id。检查 entry point class 是否可 import。
命令检查teleop command 必须是单行，且包含 --task。检查 task id 与注册内容一致。
IsaacLab smoke test当前列为可选测试计划。封装成可执行 skill：无 XR 或 mock XR 下创建 env，验证 action/observation/pipeline。

自动测试 gate 在代码里的位置

pipeline.run_generate_pipeline(...)
  ↓
generator_workflow.run_generator_workflow(...)
  ↓
如果 generated.ok == false:
  - adaptation candidate / unsupported

  ↓
post_generation_tests.run_post_generation_tests(...)

  - 否：阻断，不写文件

后续可以封装成独立 skill

这套 test gate 可以继续产品化成独立 skill，例如 env_cfg_validation。 它可以接受 generated files 和 spec，自动执行语法、注册、import、dry-run env creation、teleop pipeline mock 等检查。 

env_cfg_validation skill:
  输入：
    - generated env_cfg files
    - PickPlaceVRSpec
    - expected task id
  输出：
    - pass/fail
    - failed checks
    - smoke test logs
    - 是否允许写入正式 task registry
