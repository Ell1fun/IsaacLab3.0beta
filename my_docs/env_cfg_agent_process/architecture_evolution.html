AI Agent 生成 env_cfg：开发演进与重构

记录这个 skill 从单文件 orchestrator 到 template generator，再到模块化拆分的工程决策过程。

目录 总览 架构分层 开发演进 Schema / Spec Workflow Orchestrator 代码导读 模块与流程图 Adaptation / Test Gate Preset Enrichment Template Generator Placement Workflow Skill 文件 开发日志 落地路线

最终结论

这个 skill 的核心不是“让大模型写 env_cfg”，而是把用户自然语言变成可校验的 spec， 再用 presets、placement workflow 和 template generator 确定性生成仓库内已有机器人任务。 大模型只在自然语言理解和复杂 spec 补齐阶段作为 fallback。

当前重构目标：保持 CLI 行为不变，但把原来堆在 orchestrator.py 里的职责拆到多个模块。

阶段一：先做单文件 orchestrator

最开始我们需要快速验证“用户输入一句话，系统能路由到 skill、读 schema、补齐 spec、生成 env_cfg、注册 task、输出命令”这条闭环。 因此第一版把 route、config、LLM API、schema gate、generator、writer 都写在一个 orchestrator.py 里。

优点问题
开发快，容易跑通端到端 demo。函数越来越多，文件逐渐变成“入口 + LLM + preset + generator + writer”的混合体。
方便观察每一步输出，适合学习和探索。继续加功能会让分支复杂，难以判断某个 bug 属于哪一层。

阶段二：发现让模型直接写 env_cfg 不稳定

真实 API 跑通后，模型输出里出现大量 TODO，例如 EEF link、IK joints、hand joints、table USD、输出路径等。 这说明 schema 只约束结构，不提供仓库里的确定事实；模型不知道就只能猜或留 TODO。

  • 模型容易把路径写错，例如少一层 isaaclab_tasks。
  • 模型不敢确定 joint/link 顺序，因为这些必须和参考 env_cfg、teleop pipeline 对齐。
  • 模型生成完整 env_cfg 既慢，又容易破坏已有模板里的 IK、teleop、observation、termination。

阶段三：改成 presets + template generator

我们把机器人和物体的确定事实写进 robot_presets.yml 和 object_presets.yml。 对仓库已有完整模板的机器人，不再让模型写最终代码，而是让 template generator 继承已有 env_cfg，只覆盖任务相关参数。 

用户自然语言
  ↓
本地 spec parser 或 AI fallback
  ↓
preset enrichment
  ↓
schema gate
  ↓
template generator
  ↓
env_cfg 薄封装 / task 注册 / 启动命令
这个阶段的关键转变：模型从“代码作者”降级为“需求理解助手”；代码生成由程序模板负责。

阶段四：加入 placement workflow

后来发现 object.init_state.pos 不能只放在 object preset 里写死。 同一个水瓶换到不同机器人时，合适的摆放位置不同，应该根据机器人桌面位置和工作空间自动计算。

旧方式新方式
object preset 直接写绝对坐标。robot preset 提供 default_placement，workflow 用 table_center + offset 计算。
换机器人后可能离本体太远。不同机器人可以配置自己的工作区偏移。
模型可能猜坐标。模型只理解“靠近/居中/偏右”等意图，最终坐标由规则算。

阶段五：拆分 orchestrator

当 route、config、LLM、schema、presets、placement、template generator、writer 都放在一个文件里时， 复杂度已经不适合继续堆功能。于是我们保留 CLI 行为不变，只把内部职责拆成模块。 

env_cfg_skills/
  orchestrator.py          # CLI 入口和 chat loop
  skill_types.py           # SkillDef / LlmConfig / WorkflowConfig / OrchestratorConfig
  env_utils.py             # 路径、YAML/JSON、deep_fill 等通用工具
  registry.py              # skill registry 和 route_skill
  config_loader.py         # local config / env var / CLI override
  llm_client.py            # OpenAI-compatible / Ark responses API 调用
  schema_validation.py     # schema gate 和兜底校验
  presets.py               # robot/object presets、placement、spec enrichment
  spec_builder.py          # 本地 parser + AI fallback 补 spec
  generator_workflow.py    # template generator、注册、命令、写文件
  pipeline.py              # Stage A + Stage B 的主流水线
  starter_specs.py         # starter spec 示例

拆分后的优势

  • 职责清晰：看文件名就知道该逻辑属于哪一层。
  • 方便扩展：后续加 H1 模板，只改 presets/template generator，不动 CLI。
  • 方便排错：API 慢看 llm_client.py，坐标不对看 presets.py，输出文件不对看 generator_workflow.py。
  • 降低模型风险：LLM 调用集中在 spec builder fallback，不会散落到代码生成路径里。
  • 保留用户体验：命令仍然是 python my_docs/env_cfg_skills/orchestrator.py generate ... 或 chat --enable_api。

当前推荐心智模型

orchestrator.py 只负责“接请求和分发”
pipeline.py 负责“按 workflow 串起来”
spec_builder.py 负责“自然语言变 spec”
presets.py 负责“仓库事实和 placement”
schema_validation.py 负责“能不能进入下一步”
generator_workflow.py 负责“确定性生成代码/注册/命令”
llm_client.py 负责“唯一的模型 API 通道”
