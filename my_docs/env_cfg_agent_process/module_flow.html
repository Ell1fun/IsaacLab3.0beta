这张图叫什么

工程里通常把这种图叫 流程图（flowchart）。如果重点是系统状态变化，也可以叫 状态机图； 如果重点是一次请求从入口到结束的活动顺序，也可以叫 活动图（activity diagram）。 这里用 flowchart 表达 orchestrator 的分支决策。

模块职责总表

模块 核心职责 主要输入 主要输出 是否调 AI
orchestrator.py CLI 入口，解析命令，处理 route/template/validate/generate/chat，维持 chat loop。 终端参数、用户自然语言、--enable_api、--write。 命令输出；调用 pipeline 后得到 written_files 和 commands。 否，只把 enable_api 传下去。
registry.py 注册可用 skill，并根据用户 prompt 做关键词路由。 用户自然语言、可用 skill 列表。 选中的 SkillDef，例如 pick_place_vr。 否。
config_loader.py 读取本地配置、环境变量和 CLI override，决定 dry-run 还是写文件。 orchestrator_config.local.yml、环境变量、CLI 参数。 OrchestratorConfig。 否。
pipeline.py 串联 Stage A 和 Stage B，是一次生成请求的主流水线。 SkillDef、用户最新文本、配置、API key、是否启用 API、可选 draft_intent。 完整 workflow 输出，包含更新后的 draft_intent，成功时可裁剪成短格式。 否，自己不调；把开关传给下游。
clarification_resolver.py 维护多轮 draft_intent，把“不要水管了 / 换成水瓶 / 方向盘作为主物体”这类回答转成结构化 intent 更新；开启 API 时可接收模型输出的 intent patch。 用户最新回答、上一轮 draft_intent、object_presets.yml catalog、可选 LLM resolver payload。 更新后的 intent、deterministic errors/questions，或可转换成 spec 的 intent。 否。
object_intent.py 提供 object catalog、推荐列表和静态物体分析辅助；主要给 resolver 和追问文案复用。 object_presets.yml。 可推荐物体列表、别名 catalog。 否。
spec_builder.py 调用 clarification resolver，把通过 safety gate 的 intent 变成 PickPlaceVRSpec；再做 preset enrichment、schema gate，必要时 AI fallback。 用户最新文本、schema、draft intent、draft spec、validation errors。 结构化 spec、schema errors、追问问题、enrichment notes、更新后的 draft intent。 有条件调用：开启 --enable_api 时先调用 clarification resolver prompt；schema 不通过时还可调用 Spec Builder prompt。
presets.py 加载 robot/object/placement presets、解析继承、补齐仓库确定事实，并计算默认和语义 placement。 初始 spec、robot_presets.yml、object_presets.yml、placement_presets.yml。 enriched spec，例如 EEF、joints、USD、table、object pose、target pose、scene object poses、task id。 否。
schema_validation.py 执行 schema gate，判断 spec 是否能进入 generator。 schema、enriched spec。 错误列表；空列表表示通过。 否。
generator_workflow.py 根据通过校验的 spec 做 exact template 匹配；匹配成功生成 env_cfg/注册/命令；缺模板时抽取参考 env_cfg 的结构化片段，调用 AI 生成 adaptation_spec，再由程序确定性渲染 candidate env_cfg。 validated spec、skill、配置。 files、commands，或 adaptation_candidate。 exact template 不调 AI；缺 exact template 且 --enable_api 时调 AI 生成 adaptation_spec。
prompts/pick_place_vr_template_adaptation.md AI template adaptation 的提示词资产，定义迁移参数推断规则、结构化上下文格式、adaptation_spec JSON 格式和禁止事项。 由 generator_workflow.py 读取，和 spec/reference env_cfg snippets 一起发给模型。 模型 system prompt。 它本身不调 AI，但决定 AI adaptation 的行为。
post_generation_tests.py 自动测试 gate：生成内容写入前先做语法、TODO、注册、命令、scene objects 和 G1 trigger hand joint coverage 检查。 generated payload、validated spec。 错误列表；空列表表示允许进入写文件阶段。 否。
llm_client.py 统一封装模型 API 调用、timeout、retry、Ark responses / chat completions 兼容。 LLM 配置、API key、messages。 模型返回文本，或解析出的结构化对象。 是，唯一真正发 HTTP 给模型的模块。
skill_types.py 定义 SkillDef、LlmConfig、WorkflowConfig、OrchestratorConfig。 无运行输入，主要是类型定义。 被其他模块复用的数据结构。 否。
env_utils.py 路径、YAML/JSON、deep_fill、缺失值判断、slug 转换等通用工具。 文件路径、dict、字符串。 通用处理结果。 否。
starter_specs.py 提供 template --skill pick_place_vr 的 starter spec。 无。 示例 spec。 否。

总流程图

下面是一次 generate 或 chat 请求的完整分支。最关键的判断是： 本地 parser + presets + schema 能不能通过；能通过后还要看是否存在 exact template。 exact template 存在就不调 AI；schema 不通过且开启了 --enable_api 才进入 AI Spec Builder。 exact template 不存在但有参考模板时，如果没开 API 就只输出 adaptation candidate；如果开了 API，就先抽取参考 env_cfg 的结构化片段，再进入 AI adaptation generator 生成 adaptation_spec，最后由程序生成候选 env_cfg。

什么时候调用 AI

场景是否调用 AI原因
用户说“帮我生成一个宇树 G1 抓取水瓶的遥操任务”。 不调用。 本地 parser 能识别 unitree_g1_inspire_ftp 和 bottled_water_c01，presets 能补齐事实，schema 能通过。
用户说“傅里叶 GR1T2 抓方向盘”。 不调用。 机器人、物体、模板都在 presets 和 template map 中。
用户说复杂空间意图，例如“放在右手前方 30cm，目标放到桌子左上角”。 可能调用。 AI 适合把自然语言意图转成结构化 placement intent；最终坐标仍应由 workflow 计算。
本地 parser 识别不出机器人或物体，schema gate 不通过，但用户传了 --enable_api。 调用。 AI Spec Builder 尝试补齐 spec，或者帮助形成追问。
当前 pick_place_vr spec 已通过 schema，进入 Stage B。 不调用。 最终 env_cfg、注册和命令由 template generator 确定性生成。
机器人 preset 存在但没有已有 pick_place teleop 模板，例如当前 H1。 不应该硬调用 AI 写代码。 应该阻断并提示缺模板；后续单独做机器人接入 skill。

什么时候直接写文件

“直接写文件”不是指绕过校验，而是指不调用 AI 写代码。只有 spec 通过 schema gate，并且当前 skill 能走确定性 template generator 时，才会生成文件内容。 

可以写文件的条件：
1. route 到 pick_place_vr
2. spec builder 得到结构化 spec
3. presets 补齐 robot/object/table/placement/task 信息
4. schema_validation 通过
5. 进入可生成路径：
   - exact template：fourier_gr1t2_high_pd -> PickPlaceGR1T2EnvCfg
   - exact template：unitree_g1_inspire_ftp + handtracking -> PickPlaceG1InspireFTPEnvCfg
   - exact template：seres_r11_a2_high_pd + handtracking -> PickPlaceR11EnvCfg
   - exact template：seres_r11_a2_high_pd + controller -> PickPlaceR11TriEnvCfg
   - adaptation：unitree_g1_inspire_ftp + controller -> AI adaptation_spec + deterministic candidate env_cfg
6. post_generation_tests 通过
7. dry_run=false，也就是用户显式传了 --write
不传 --write 时，只会输出 DRY_RUN:/abs/path。这是为了避免 demo 阶段误改仓库文件。

一句话总结

当前工程的策略是：让 AI 理解需求，不让 AI 直接写最终 env_cfg；让 presets 承载仓库事实，让 template generator 负责确定性代码生成。
