env_cfg 的目的和内容

env_cfg 解决“机器人在什么任务里做什么”：场景、动作、观测、终止、事件（reset/随机化）、仿真频率等。

目录 总览 assets 清单 robot cfg env_cfg teleop pipeline actuator / regex 扫盲 坐标系/关节轴 任务注册 验证与调试 R11 对照

典型组成

配置块 作用 通常写什么
SceneCfg 世界里有什么 机器人、桌子/地面、物体、灯光、相机/传感器、env spacing
ActionsCfg 外部动作如何作用到机器人 关节位置/速度/力矩、IK action、手爪 action、teleop action
ObservationsCfg policy 能看到什么 关节状态、root 状态、物体状态、末端位姿、相机图像、上一帧 action
RewardsCfg RL 奖励 距离/姿态误差、成功奖励、能耗、平滑项
TerminationsCfg 何时结束 episode 超时、失败（掉落/摔倒）、成功
EventCfg reset 与随机化 重置机器人/物体、随机化位姿/质量/摩擦、重置 joint target
EnvCfg 把上面拼成一个环境 sim.dt、decimation、episode_length_s、physics buffer、teleop

env_cfg 里为什么需要 joint_names（以及从哪里来）

env_cfg 需要频繁“选中一批关节/连杆”来做动作、观测、重置与成功判定。因此会出现各种 joint_names（字符串列表）或 joint_names_expr（正则表达式列表）。 这些名字通常来自两处：robot cfg（复用通用分组）与 env_cfg（为任务定义顺序/子集）。

来源 适合放什么 为什么 R11 里的例子
robot cfg（isaaclab_assets/robots） 通用分组/可复用语义 一处定义，多任务复用；避免每个 env_cfg 重复写 HAND_JOINT_NAMES 从 robot cfg 直接复用
env_cfg（任务侧） 任务专用子集、严格顺序列表 动作与观测通常需要固定维度与固定顺序；正则匹配顺序不稳定且可读性差 R11_ARM_JOINT_NAMES 在 env_cfg 内显式列出并用于 IK 控制
你在 robot cfg 里看到的 joint_names_expr（正则）更偏“批量配置 actuator”；而 env_cfg 里的 joint_names 更偏“定义 action/observation 的维度和顺序”。 两者都在选关节，但目的不同。

joint_names 在 env_cfg 里会用在什么地方（不止 IK）

用法 你在干什么 R11 pick-place 的具体例子
IK / 任务空间动作 指定 IK 控制哪些关节、nullspace 用哪些关节做姿态偏好 PinkInverseKinematicsActionCfg(pink_controlled_joint_names=R11_ARM_JOINT_NAMES) 与 NullSpacePostureTaskCfg(controlled_joints=...)
关节空间动作 只控制某一部分关节（例如只控手、或冻结下半身） 常见做法是把下半身关节放进“固定/排除列表”，动作空间不包含它们
观测（Observations） 从机器人状态里只取需要的关节子集，保证维度稳定 R11_HAND_JOINT_NAMES 用于手部关节状态观测（维度固定）
reset / 初始化（Events） 按名字写 init_state.joint_pos、或重置时只改一部分关节 例如把下半身关节固定在站姿（R11_FIXED_JOINT_POS）
调试与映射 把“字符串名字”映射到关节索引，打印/记录某些关节曲线 常用 find_joints(joint_names) 在运行时解析索引
结论：env_cfg 确实会复用 robot cfg 里定义的 joint_names（比如手指），IK action cfg 也会用到关节名列表，但 joint_names 在 env_cfg 的用途远不止 IK。

Nullspace 是什么？为什么 IK 里要写 nullspace joints

在 IK（逆运动学）里，控制目标通常是末端位姿（例如 6 维：位置 3 + 朝向 3）。如果可控制的关节自由度多于任务约束，就会出现“解不唯一”： 在不改变末端位姿的前提下，关节还能在某些方向上自由调整。这些“不影响主要任务的自由方向”就叫 nullspace（零空间）。

利用 nullspace 的典型目的，是在满足末端任务的同时，做一些“次要目标”（secondary objective），例如：

  • 保持更自然/更稳定的姿态（例如肘部不要外翻、手臂不要扭到极限）。
  • 远离关节限位（降低触发 joint limit 的概率）。
  • 减少自碰撞或避免某些危险姿态。

在 R11 pick-place 的 ActionsCfg 里，Pink IK controller 配了 NullSpacePostureTaskCfg，并显式指定了哪些关节参与这个“姿态偏好”任务： controlled_joints=R11_NULLSPACE_JOINT_NAMES（也就是你看到的那份列表）。 这份列表的意义是：当末端目标有冗余时，IK 会在这些关节上“顺便”把姿态往一个更合理的方向拉一拉。

在当前实现里，nullspace joints 主要选的是肩/肘 + 腰：让大关节承担姿态调整；手腕关节更直接影响末端朝向，通常不放进 nullspace，避免末端姿态更“飘”。 这不是硬规则，但属于常见的工程取舍。
直觉总结：主要任务（FrameTask）决定“手到哪里”；nullspace 任务决定“手到那里时身体怎么摆更舒服/更安全”。如果没有 nullspace，你会更容易看到奇怪的肘部姿态或关节贴着限位走。

手指控制：为什么会有 OPEN/CLOSED pose（而不是直接用 OpenXR 手指关节角）

你在 R11 pick-place 的 env_cfg 里会看到 R11_HAND_OPEN_POSE / R11_HAND_CLOSED_POSE 两组字典。 它们的作用不是“把 OpenXR 手追踪的每个关节角直接喂给机器人”，而是为 motion controller（只有扳机/按键，没有完整手指关节追踪）提供一个简化的抓握控制：

  • 输入：一个 grasp 标量（例如 trigger，范围通常是 [0, 1]）。
  • 输出：手指关节目标角（对字典里列出的关节做 open → closed 线性插值）。
  • 未列出的关节：保持默认值（通常是 0.0）。
在这份仓库里同时存在两条 teleop 路线：手追踪版本用 DexHandRetargeter 把 OpenXR 手骨架/姿态映射到机器人手指关节； motion controller 版本则用扳机插值的 OPEN/CLOSED pose 做“整手抓握”。 两者都能控制手，但输入信号的分辨率和映射复杂度不同。

如何读懂 teleop：从 OpenXR 输入到 env action 的“管线”

如果你想理解“遥操到底怎么实现”，最关键要读的就是 env_cfg 里构建 retargeting pipeline 的函数（例如 _build_r11_pickplace_pipeline）。 这段代码把 OpenXR/CloudXR 的输入（手追踪/手柄）转换成一个固定布局的一维 action tensor，最后喂给 ActionsCfg。

  1. 选择输入源：手追踪用 HandsSource，手柄用 ControllersSource。
  2. 对齐到仿真世界：用 world_T_anchor 把 XR anchor 坐标系变换到 world。
  3. 末端位姿 retarget：Se3AbsRetargeter 产生左右手 EEF 的 pose(7)，并用 target_offset_* 对齐 frame 约定。
  4. 起点重定位：R11WristPoseRebaser 把“绝对 pose”转换为“以 idle_pose 为中心的相对控制”。
  5. 手指 retarget：手追踪版本用 DexHandRetargeter 输出手指关节；手柄版本用 trigger 插值 OPEN/CLOSED。
  6. 合并与重排：TensorReorderer 把多个输出拼成一个 action，并保证顺序严格匹配 ActionsCfg.upper_body_ik 的期望。
读 teleop 的关键不是“某一行 API 怎么用”，而是确认：输入来自哪里 → 经过哪些坐标系变换/offset → 输出 action 的布局是什么 → ActionsCfg 期望什么布局。

DexPilot 是什么？在这里起什么作用？

在 R11 的手追踪遥操管线里，DexPilot 指的是一种“手指重定向（finger retargeting）”的方法/配置类型： 它把 OpenXR 的手追踪骨架信息（尤其是指尖位置/姿态）映射成机器人手指关节目标角度。

你们在 assets/seres_r11/revo2_left_hand_dexpilot.yml 里能看到它的核心字段：

  • type: DexPilot：说明使用 DexPilot 这套重定向逻辑。
  • finger_tip_link_names：指定手指触点/指尖 link（用于计算重定向目标）。
  • target_joint_names：指定要输出/控制的手指关节名。
  • wrist_link_name：手部 URDF 的基准 link。
因此这里的 “DexHandRetargeter + DexPilot YAML” 相当于：用一份手部 URDF + 一份重定向配置，告诉系统如何把人手的指尖运动变成机器人手指关节角。 这就是“你以为可以直接用 OpenXR 手指关节角”背后真正需要的那层映射逻辑。

为什么 EEF 用的是 wrist_yaw_Link？还会有别的 Link 吗？

这部分涉及坐标系、关节轴、欧拉角约定。想一次性把概念理顺：看 坐标系/关节轴。

会有别的 Link。URDF/USD 里每个关节（Joint）通常连接两个刚体（Link）：父 Link 与子 Link。 很多机器人会把一段串联的关节按“roll/pitch/yaw”命名，于是就会出现 ..._wrist_roll_Joint、..._wrist_pitch_Joint、..._wrist_yaw_Joint， 以及对应的子 Link：..._wrist_roll_Link、..._wrist_pitch_Link、..._wrist_yaw_Link。

roll / pitch / yaw 分别是哪三个方向？怎么区分？

roll/pitch/yaw 本质上是“绕某个坐标轴的旋转”的人类命名方式。最常见的右手系约定是：

  • roll：绕 X 轴旋转（像飞机左右机翼上下翻滚）。
  • pitch：绕 Y 轴旋转（像飞机抬头/低头）。
  • yaw：绕 Z 轴旋转（像指南针转向）。
但要注意：这只是“常见约定”。在机器人模型里，最权威的区分方法不是看名字，而是看 URDF/USD 给该关节定义的旋转轴（URDF 的 <axis xyz="...">）。 名字可能叫 yaw，但实际轴向仍以模型文件为准。

你提到的“手竖着/横着放”：roll 还是不是同一个方向？

关键在于：你说的 X/Y/Z 是哪个坐标系的轴。常见有两种坐标系：

  • 世界坐标系（world frame）：固定不动的 X/Y/Z。
  • 物体/手腕坐标系（body/end-effector frame）：跟着手一起转的 X/Y/Z。

如果你把 roll/pitch/yaw 定义为“绕世界坐标系的轴转”（外旋/Extrinsic），那世界 X/Y/Z 当然不变。 但如果你把 roll/pitch/yaw 定义为“绕物体自身坐标系的轴转”（内旋/Intrinsic，更常见于“物体姿态的欧拉角”表达）， 那当手的姿态变了，手自身的 X/Y/Z 也跟着变，同一个 roll 数值对应的空间旋转方向就会变。

这就是为什么“roll 对齐 X、pitch 对齐 Y、yaw 对齐 Z”这句话必须补一句前提：对齐的是“哪个 frame 的 X/Y/Z”，以及欧拉角采用的顺序与内旋/外旋约定。 实际系统里最好用四元数/旋转矩阵来存姿态，roll/pitch/yaw 更多用作人类可读的显示方式。

在 R11 的 URDF（assets/seres_r11/r11_0615.urdf）里，你能看到腕部确实包含这三段 Link： left_wrist_roll_Link、left_wrist_pitch_Link、left_wrist_yaw_Link（右手同理）。

EEF（末端执行器）到底怎么决定用哪个 Link？

EEF 其实就是你希望 IK/控制器“对齐的目标坐标系 frame”。怎么选通常看任务语义：

  • 如果你把“手腕末端”当末端：通常选腕部链条最后一节（这里就是 ..._wrist_yaw_Link）。
  • 如果你把“抓取点/工具中心点（TCP）”当末端：最好在 URDF/USD 里增加一个固定的 tool/grasp link（或用一个固定变换 offset），让 EEF 对齐到真正的抓取点。
  • 如果你想用手指触点做精细任务：可以选某个 ..._touch_link，但 IK 的意义会变成“让某根手指末端去对齐目标”。
实用原则：EEF 选“你要控制的几何点/姿态”所在的 frame；它应当在 URDF/USD 中存在、命名稳定，并且在动作/观测里保持一致。

pick-place 任务把 left_wrist_yaw_Link/right_wrist_yaw_Link 作为 EEF（末端执行器）frame 的原因很朴素： 它是腕部链条的最末端 link，用它作为“手腕末端坐标系”更符合直觉，也更稳定（frame 跟随关节链条走到最后一节）。 当然你也可以选别的 link（比如 ..._wrist_pitch_Link 或某个手指触点 link）作为 EEF， 但那会改变 IK 的目标 frame（也就改变了动作定义与任务意义）。

推荐编写顺序（最省时间的方式）

  1. 先只写 SceneCfg：只 spawn 机器人 + 地面，确认不爆炸。
  2. 再加任务物体/桌子/目标区域：确认高度和坐标系正确。
  3. 加最小 ActionsCfg：先让机器人能动（哪怕是固定动作）。
  4. 再切到你真正需要的 action：例如 IK、teleop、学习算法动作空间。
  5. 补 ObservationsCfg：先保证维度稳定、名字匹配（regex/关节名）。
  6. 补 TerminationsCfg + EventCfg：episode 能 reset、能结束、成功/失败判断合理。
  7. 最后补 rewards/curriculum/randomization。
如果你的目标是 teleop/模仿学习采集数据，rewards = None 也可以；强化学习训练才必须有 rewards。
