坐标系与关节轴（Link / Joint / EEF）

把你刚问到的“roll/pitch/yaw 到底对谁、axis xyz 是啥、joint frame 怎么来、EEF 该怎么选”用一套清晰的分层说透。

1) 三个最常用的坐标系：World / Link / Joint

名字 它是谁 是不是固定不动 你在工程里什么时候关心它
World frame 仿真世界的参考坐标系 固定 放置机器人/物体、读取位姿、定义目标点
Link frame 每个刚体（link）的局部坐标系 随刚体运动 读取某个 link 的姿态、做接触/传感、定义 EEF 候选 frame
Joint frame 每个关节（joint）的局部坐标系 跟着父 link 运动；相对父 link 的定义固定 理解 URDF 的 origin/axis、判断关节转轴方向
经验法则：你在控制/IK 里大多关心“某个 frame 在 world 里的位姿”；而当你解释 URDF 时，最容易混淆的是“axis 到底在哪个 frame 里表达”。

1.5) XR 里的 anchor 坐标系是什么？什么是 world_T_anchor？

在 XR（OpenXR/CloudXR）里，手/手柄的追踪数据往往不是直接在仿真 world 坐标系下给出的，而是在一个 XR 的“参考空间”里给出的。 这个参考空间在你们的遥操管线里通常称为 anchor frame（锚点坐标系）。

world_T_anchor 是一个 4×4 齐次变换矩阵，表示“anchor 坐标系到仿真 world 坐标系”的变换： 

p_world = world_T_anchor @ p_anchor

直觉上它做的事情是：把 XR 空间里测到的手的位置/朝向，搬到仿真世界的正确位置（并对齐坐标轴约定）。 如果不乘这个矩阵，你拿到的 pose 仍然在 XR anchor 下，直接当作机器人末端目标会出现“方向不对/位置飘/整体偏移”的问题。

在 IsaacTeleop 里，设备层会把目标 rebase 矩阵和 world_T_anchor 组合起来喂给管线： target_T_world @ world_T_anchor。其中 world_T_anchor 负责把 XR anchor 对齐到 world，target_T_world 则可以把输出再重定位到另一个目标 frame（例如机器人 base）。

2) URDF 里 joint 的 parent/child/origin/axis 分别是什么意思

以一段典型 URDF 为例：

<joint name="left_hip_pitch_Joint" type="revolute">
  <origin xyz="..." rpy="..." />
  <parent link="pelvis" />
  <child link="left_hip_pitch_Link" />
  <axis xyz="0 -1 0" />
</joint>
  • parent/child：这个关节连接的两个 link。关节把 child “挂”在 parent 上。
  • origin xyz/rpy：定义 joint frame 相对 parent link frame 的位姿（位置+朝向）。
  • axis xyz：revolute 关节的转轴方向向量，表达在 joint frame 里。0 -1 0 意味着“绕 joint 的 -Y 轴转”。
很多人会误以为 axis 是对 world 或直接对 parent 的轴。更准确的说法是：它先定义在 joint frame；而 joint frame 的朝向由 origin rpy 相对 parent 决定。

3) 右手系与转动正方向（为什么 axis 有正负号）

URDF 的关节角正方向遵循右手定则：右手大拇指指向 axis 向量方向，其余四指弯曲方向就是关节角增大的方向。 因此 axis 写 (0, -1, 0) 与写 (0, 1, 0) 会导致“正角度方向”相反。

调试技巧：如果你发现某个关节控制方向完全反了，第一优先检查就是 axis 的符号，以及上层 action/控制器对关节角正方向的约定是否一致。

4) roll/pitch/yaw 到底对哪根轴？为什么“手横竖放”会让直觉出错

roll/pitch/yaw 是欧拉角的俗称，常见说法是 roll 对 X、pitch 对 Y、yaw 对 Z。但这句话必须补两个前提：

  • 对齐的是哪个 frame 的 X/Y/Z（world 还是物体/EEF 自身）。
  • 欧拉角顺序与约定是什么（内旋 intrinsic 还是外旋 extrinsic，以及 XYZ/ZYX 等顺序）。

你的“手竖着/横着放”的困惑，通常来自于：姿态的 roll/pitch/yaw 是按“物体自身 frame（随物体一起转）”的内旋定义出来的。 当手整体姿态改变时，它自身的 X/Y/Z 也改变，同一个 roll 数值对应的空间旋转方向自然会变。

在工程实现里，姿态更可靠的表示是四元数或旋转矩阵；roll/pitch/yaw 更适合作为人类可读的显示，不适合作为“唯一的真理”去推导关节轴。

5) “joint 名字里的 yaw/roll/pitch” vs “URDF 的 axis”

在你们的 R11 代码里经常出现 ..._hip_yaw_Joint、..._hip_roll_Joint、..._hip_pitch_Joint。 这些后缀首先是“语义命名”，用于让人读起来知道这是髋关节链条的三个自由度。

一个常见误解是把它直接等价成“yaw=绕 joint 的 Z、roll=绕 joint 的 X、pitch=绕 joint 的 Y”。这种等价在某些约定下可能成立，但在工程里不可靠：

  • 名字只是语义标签，不能保证和某个固定轴一一对应。
  • URDF 的 axis xyz 才是 revolute joint 的真实转轴（而且是定义在 joint frame 里）。
  • joint frame 的朝向由 origin rpy 相对 parent link 定义，因此即使 axis 写成 (0, 0, 1)，它在世界里也会随 parent 姿态变化。
最权威的“到底绕哪根轴转”来自 URDF/USD 的轴定义（URDF 的 <axis xyz="...">），而不是名字里写了 yaw/roll/pitch。 这也是为什么你会看到某些关节名字叫 yaw，但 axis 并不是 (0, 0, 1)。

R11 例子：为什么 left_hip_yaw_Joint 的 axis 看起来是绕 X，但名字却叫 yaw？

以 R11 的这段为例（left_hip_yaw_Joint）： 

<joint name="left_hip_yaw_Joint" type="revolute">
  <origin ... rpy="-3.14159059 1.46160946 0.00000206" />
  <parent link="left_hip_roll_Link" />
  <child link="left_hip_yaw_Link" />
  <axis xyz="1 0 0" />
</joint>

这里的 axis xyz="1 0 0" 不是“绕世界 X 轴”，甚至也不是“绕 parent link 的 X 轴”，而是绕 joint frame 的 X 轴。 而 joint frame 的朝向由 origin rpy 定义：它相对 parent link 有一个很大的旋转（这里接近 -π 和 ~84°）， 所以 joint 的“X 轴”在 parent/world 里可能已经被转到你直觉里的“竖直方向”附近。

换句话说：名字里的 yaw 往往表达的是“这个自由度在人体/机器人语义上是 yaw（水平转向/绕竖直轴的那一段）”， 但它在 URDF 中具体用 (1,0,0) 还是 (0,0,1) 来写，取决于导出时选择的 joint frame 定义（origin rpy 怎么摆）。

判断“它在世界里是不是绕竖直轴 yaw”的正确方式是：把 joint frame 的旋转（origin rpy）和 parent/world 的姿态一起考虑，把局部轴 (1,0,0) 变换到 world 再看方向。 因此不要用“axis 数字长得像 X/Y/Z”去推断 yaw/roll/pitch 的语义。

一个好用的心智模型：名字描述“语义”，axis 决定“物理真相”

你可以这样记：很多机器人把关节命名成 yaw/roll/pitch，并不是在声明“它严格绕 world 的 Z/X/Y 轴转”，而是在描述它在站姿/零位附近的运动语义：

  • yaw：更像“在水平面转向/扭转”的自由度（站姿附近看起来接近绕竖直方向）。
  • roll：更像“左右侧倾/侧摆”的自由度。
  • pitch：更像“前后摆动/屈伸”的自由度。
但工程上不要用名字推轴。真正的转轴来自 URDF/USD 的 axis（在 joint frame），而 joint frame 又由 origin rpy 定义。 所以“语义命名”与“固定世界轴”不是一回事。

6) EEF（末端执行器 frame）怎么选：为什么 R11 用 wrist_yaw_Link

EEF 在这里指“IK/控制器对齐的目标 frame”。它不要求一定是最后一节 link，但必须是一个你能稳定拿到位姿的 frame。

你想控制什么 推荐 EEF frame 原因
手腕末端 腕部链条最后一节（如 ..._wrist_yaw_Link） 语义清晰、命名稳定、对多数操控任务够用
抓取点 / 工具中心点（TCP） 独立的 tool/grasp frame（URDF/USD 新增固定 link 或固定 offset） 让 IK 目标对齐到真正接触点，减少“手腕对齐了但抓取点偏了”的误差
指尖/触点 某个手指末端 link（例如 ..._touch_link） 适合精细操作，但会改变动作语义：不再是手腕控制
在 R11 这个 pick-place 配置里，用 left_wrist_yaw_Link/right_wrist_yaw_Link 作为 EEF 的核心原因是：它们是腕部 roll/pitch/yaw 串联链条的末端 link，适合作为“手腕末端 frame”。

7) 工程里常见的“pose(7)”表示：位置 + 四元数

在你们的 R11 pick-place 配置里，经常会看到一个长度为 7 的 pose 元组，例如： (x, y, z, qx, qy, qz, qw)。这表示：

  • 前三个：位置 (x, y, z)（通常单位是米）。
  • 后四个：姿态四元数 (qx, qy, qz, qw)（这是 SciPy Rotation.from_quat 的顺序）。
这不是欧拉角（roll/pitch/yaw），四元数没有“分别对应某个轴”的直觉分量意义。它表示的是一个整体旋转。 至于这个 pose 是“在 world 里”还是“在某个局部 frame 里”，需要看产生/使用它的模块：例如 teleop retargeting 里通常是相对 world 的 EEF 目标位姿。

7.5) 什么是 SE(3)？为什么叫 Se3Abs？

SE(3) 指的是三维空间中的“刚体位姿”（Rigid Transform）：包含 3D 平移 + 3D 旋转。 在工程实现中，它通常用以下等价表示之一表达：

  • 4×4 齐次变换矩阵（同时包含旋转矩阵 R 与平移 t）。
  • pose(7)：位置 (x,y,z) + 四元数 (qx,qy,qz,qw)。

因此 Se3AbsRetargeter 可以直觉理解为： 把输入设备（OpenXR 手追踪/手柄）的“绝对 SE(3) 位姿”映射成机器人末端执行器的“绝对位姿目标”。

  • Se3：输出的是 3D 位姿（平移+旋转）。
  • Abs：Absolute（绝对），与 Rel（Relative，相对/增量）对应。
绝对（Abs）模式：输入 pose 直接决定输出目标 pose。 相对（Rel）模式：输入 pose 的变化量（delta）决定输出目标的增量，更像“手柄推动一下，末端走一点”。

8) R11 的 idle wrist pose 是怎么用的（rebase 逻辑）

在 R11 pick-place 的 teleop/retargeting 管线里，R11_LEFT_IDLE_WRIST_POSE/R11_RIGHT_IDLE_WRIST_POSE 用来把“手追踪的绝对位姿” 重新居中到机器人一个中立（idle）腕部姿态上。其核心思路就是你说的：用“变化量（delta）”叠加到 idle pose 上。

逻辑可以用下面三步概括（对应 R11WristPoseRebaser 的实现）：

  1. 记录开始时刻的手追踪 pose：start_pose（位置与四元数）。
  2. 每帧计算相对变化量：delta_pos = raw_pos - start_pos，delta_rot = raw_rot * inv(start_rot)。
  3. 输出目标 wrist pose：target_pos = idle_pos + delta_pos，target_rot = delta_rot * idle_rot。
这个 rebase 过程的好处是：无论操作者一开始站在什么姿态/位置，都能让“开始动作”的目标对齐到机器人预设的 idle wrist pose，避免一上来手就跳到奇怪位置。

这段代码能不能复用？能，但要明确它依赖的“前提”

这种“记录起始 pose → 用 delta 叠加到 idle pose”的结构是非常通用的：换机器人、换任务都可以复用。 但它看起来简单，是因为很多关键假设被隐藏在上下游里；复用时最容易踩坑的点通常在这些前提上：

  • 同一参考系：raw_pose、start_pose、idle_pose 必须表达在同一个 frame 下（通常是 world 下的 EEF 目标）。如果上游在 XR anchor，下游在 world，就必须先做 world_T_anchor 变换。
  • 同一姿态约定：这里使用的是四元数 (qx,qy,qz,qw)（SciPy 的顺序）。如果换成 (qw,qx,qy,qz) 或欧拉角，会直接错。
  • 乘法顺序不随便换：delta_rot = raw * inv(start) 与 inv(start) * raw 的意义不同；target = delta * idle 与 idle * delta 也不同。
  • idle pose 的语义：idle_pose 必须对应“机器人想要的中立末端 frame”（例如 wrist_yaw_Link）。换了 EEF link 或换了手工具中心点（TCP），idle_pose 也要跟着换。
  • 重置与启动逻辑：这里在 reset/非 RUNNING 时清空 start_pose，并输出 idle。不同任务可能需要不同的触发条件，否则会出现“突然重新归零”的手感。
  • 安全约束：这段本身不做 workspace 限制、速度限制、碰撞/自碰撞处理；不同机器人/任务往往需要在下游加 clamp/滤波/限速。
实用结论：这段可以当作一个可复用的“rebase 模块”。复用时不要只复制代码本体，更要对齐 frame、四元数顺序、EEF 定义和 reset 语义。
