Teleop Pipeline：对比与抽象

对比 R11 与 Unitree G1 Inspire Hand 的 pick-place 遥操 pipeline 写法，解释它们为什么不同，并给出“抽象成一套通用写法”的拆分思路与复用边界。

共同骨架：它们本质上是同一种数据流

这两个文件虽然细节不同，但骨架基本一致：

  1. 输入源：OpenXR 手追踪（HandsSource）。
  2. 坐标系对齐：外部输入 world_T_anchor，把 XR anchor frame 变换到仿真 world。
  3. 腕部末端：两个 Se3AbsRetargeter 分别输出左右腕的 ee_pose(7)。
  4. 手指：两个 DexHandRetargeter 输出左右手指关节目标。
  5. 拼 action：TensorReorderer 把多个输出拼成一个一维 action，并保证顺序与 env 的 action space 一致。
因此你可以把 “pipeline builder” 理解为：把一堆异构输入（两只手的 pose + 两只手的关节）组合成一个固定维度、固定顺序的 action 张量。

差异对比：R11 vs G1 Inspire Hand

维度 R11（seres_r11） Unitree G1 Inspire Hand 为什么会不同
函数入口 _build_r11_pickplace_pipeline() _build_g1_inspire_pickplace_pipeline() 不同机器人/任务文件各自封装。
腕部坐标补偿 左右腕都有 target_offset_roll/pitch/yaw（并且左右 pitch 取反）。 左右腕 offset 不同（左 pitch=90，右 roll=180、pitch=-90）。 OpenXR 追踪 frame 与机器人 USD 里 “task frame / EEF frame” 的对齐关系不同。
是否做 rebase（idle pose） 有：R11WristPoseRebaser 把绝对 pose 重定位到 R11_*_IDLE_WRIST_POSE 附近。 无：Se3Abs 输出直接进入 reorder。 是否需要“启动不跳变”的体验取舍，以及上游 retargeter 的零位对齐是否已经足够。
DexPilot 配置来源 仓库内固定路径：assets/seres_r11/revo2_*_dexpilot.yml + revo2_*_hand.urdf。 配置来自 Isaac Lab 内置 retargeter 数据目录；URDF 通过 retrieve_file_path 从 Nucleus 下载到本地。 G1 是 Isaac Lab 已支持的设备/资产生态，R11 属于项目侧集成资产。
手指 DOF 与命名 每手 11 DOF（proximal/distal + thumb）。 每手 12 DOF（thumb yaw/pitch/intermediate/distal + 四指 proximal/intermediate）。 真实手机构不同，DexPilot/URDF 的 target joints 必然不同。
action 维度 左右腕 7+7 + 手指 22（两手 11+11）。 左右腕 7+7 + 手指 24（两手 12+12）。 由手指 DOF 决定；同时必须匹配各自 env 的 action space。
TensorReorderer 的 output_order 显式把“proximal/ distal/ thumb”分段拼接。 同样分段拼接，但 joint 名与段落不同。 为了与 action space 的顺序严格一致，通常必须手写。

如何抽象成一种写法（推荐拆成 3 层）

把 pipeline builder 抽象时，建议按下面三层拆，避免“抽象过度导致每次都要魔改”。

Layer A：固定骨架（通用）

  • 输入源：HandsSource / ControllersSource。
  • 坐标系对齐：统一接收 world_T_anchor 并调用 .transformed(...)。
  • 左右腕：两路 Se3AbsRetargeter。
  • 手指：两路 DexHandRetargeter 或 trigger 插值 retargeter。
  • 拼 action：TensorReorderer + OutputCombiner。

Layer B：机器人/手的“资产参数”（换本体就会变）

  • EEF frame 对齐参数：target_offset_roll/pitch/yaw（左右手各自一套）。
  • 是否 rebase：以及左右 idle_pose(7)。
  • DexPilot YAML 路径、手 URDF 路径。
  • 左右手 hand_joint_names（并与 YAML/URDF 一致）。

Layer C：任务/控制“接口契约”（换任务就会变）

  • action layout：一维 action 的维度与顺序（由 env 的 ActionsCfg 决定）。
  • 是否需要双臂/单臂，是否要控制腰/头等额外 DOF。
  • 是否需要安全约束（速度限幅、workspace clamp、过滤抖动）。
最常见的抽象形态是：写一个 TeleopPipelineParams（纯数据）+ 一个 build_pickplace_pipeline(params)（固定骨架），每个机器人 env_cfg 只负责填 params。

什么时候需要改 pipeline？什么时候能复用？

需要改的典型场景

  • 换机器人本体导致 EEF frame/手结构变化：需要改 offsets、idle_pose、DexPilot/URDF、hand_joint_names、output_order。
  • 换手（Revo2 → Inspire → 夹爪）：手指 DOF/命名变化，必然改 Dex 配置与 action 维度。
  • 换遥操模式（手追踪 → 手柄）：输入源从 HandsSource 换 ControllersSource，并且手指控制从 Dex 变成 trigger 插值或别的映射。
  • 换任务接口（action space 变化）：比如从双臂改成单臂、从末端位姿改成关节空间控制，output_order 必须重做。

可以基本复用的典型场景

  • 任务接口不变（仍是 “左右腕 pose + 手指关节”），只是调 offsets/idle_pose：骨架可复用。
  • 同一只手结构，换场景/换奖励/换 reset：pipeline 通常不用动。
  • 仅更换资产路径（URDF/YAML 位置变化），关节名与维度不变：只改路径配置即可。
复用的前提是“接口契约一致”：action 的维度、顺序、frame 语义一致。只要这三件事有一个变了，就算函数还能跑，控制体验也会明显不对。
